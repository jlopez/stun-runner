# Hardware and code map

**Date**: 2026-11-04. **Source of every claim**: MAME 0.289 (brew), `src/mame/atari/harddriv.cpp`, `harddriv.h`, `harddriv_m.cpp`, `harddriv_v.cpp`, `atarijsa.cpp`; line numbers are those of the master branch on 2026-11-04. The brief that opened this repo expected the atarig1 driver (68010 + JSA II + RLE motion objects + SLOOP); that was wrong on three of four counts and it changes the shape of the project. This document records what the driver actually says.

## 1. The board set

S.T.U.N. Runner runs on Hard Drivin' hardware, not on a sprite/tilemap board (`harddriv.cpp` header, "the multisync board (A046901)"; `GAME(1989, stunrun, …, stunrun_machine, …)` at line 5375; MAME `-listxml stunrun` gives `sourcefile="atari/harddriv.cpp"`). Three boards:

| Board | Atari part | Processors | MAME |
|---|---|---|---|
| **Multisync** main board | A046901 | 68010 at 8 MHz (32 MHz / 4), TMS34010 GSP at 48 MHz, TMS34012 PSP (SCX6218UTP) pixel expander, ADC0809, MC68681 DUART, two 2 KB NVRAMs, 512 KB VRAM | `multisync_nomsp()` line 1538, `driver_nomsp()` line 1460, `stunrun_board_device_state::device_add_mconfig` line 1859 |
| **ADSP II** board | A047046 | ADSP-2100 at 8 MHz (32 MHz / 4), 8K-word program RAM, 8K-word data RAM, serial object ROMs, serial output RAM | `adsp()` line 1595, `init_adsp()` line 4819 |
| **JSA II** sound board | | 6502 at 1.789 MHz (3.579545 MHz / 2), YM2151 at 3.579545 MHz, OKI M6295 at 1.193 MHz (configured pin 7 high, but /WRIO bit 3 sets pin 7 at run time and MAME's runs keep it low, 7231 Hz: docs/10-adpcm.md section 2) | `atari_jsa_ii_device::device_add_mconfig`, `atarijsa.cpp` line 919 (the M6295 at 935) |

No MSP (the second TMS34010 of the Hard Drivin' Compact): `multisync_nomsp`, and `hd68k_msp_io_r` returns 0xFFFF when the device is absent (`harddriv_m.cpp` line 171). **No security chip**: the base config instantiates slapstic 117 for Hard Drivin', and the stunrun board removes it (`config.device_remove("slapstic")`, line 1864); no `init_stunrun` handler installs a SLOOP or slapstic range (lines 5082-5096). The SLOOP in the same file belongs to Steel Talons (`steeltal_init_common`, line 5208; `136087-9001.bin GAL6001 … (SLOOP)` in the Steel Talons sets). The GSP "protection" write handler is only installed for Race Drivin' Compact, Steel Talons and Street Drivin' (lines 5144, 5172, 5230, 5279). What the driver does install for stunrun are **speedups**, MAME-side optimisations that spin the CPU when it idles at a known address, which are a useful map of hot loops: GSP writes at bit addresses 0xFFF9FC00 and 0xFFFCFC00 with the idle PC 0xFFF41070, and the ADSP read of data word 0x1FFF (lines 5088-5095).

Consequence for the decompilation: **there are no graphics ROMs**. Every pixel is drawn by the GSP into VRAM from polygon data; the "pseudo-3D tunnel" is real 3D geometry transformed by the ADSP-2100. The project spans four instruction sets: 68000 (68010 variant), TMS34010, ADSP-2100 and 6502.

## 3. The 68010 address space

`multisync_68k_map` (line 599) plus the handlers `init_multisync` (line 4799) and `init_adsp` (line 4819) install at start. The data bus is 16 bits; "high byte" means D8-D15, the even address.

| Range | Access | What | MAME |
|---|---|---|---|
| 000000-0BFFFF | R | program ROM, the 12 files interleaved | `map(0x000000, 0x0fffff).rom()` |
| 600000-603FFF | R/W, high byte | JSA II: read the sound CPU's response byte, write a command byte | `init_multisync`, `atari_jsa_base_device::main_response_r / main_command_w` |
| 604000-607FFF | R | reset the sound board (any read) | `hd68k_sound_reset_r` |
| 604000-607FFF | W | **NWR latch**: address bits 0-2 pick the line, bit 3 is the value, data ignored. 0 CR2, 1 CR1, 2 LC1, 3 LC2, 4 ZP1, 5 ZP2 (NVRAM write protect), 6 /GSPRES (GSP reset), 7 /MSPRES | `hd68k_nwr_w` |
| 608000-60BFFF | W | watchdog | |
| 60C000-60FFFF | R | **port 0**: bit 0 DIAGN jumper, 1 /HSYNC, 2 /VSYNC, 3 EOC12, 4 EOC8 (ADC done), 5 self-test, 6 coin 2, 7 coin 1, 8-15 DIP SW1 (8…1) | `hd68k_port0_r`, `INPUT_PORTS_START(stunrun)` line 1084 |
| 60C000-60FFFF | W | acknowledge the level-5 timer interrupt | `hd68k_irq_ack_w` |
| 800000-807FFF | R/W | **ADSP program RAM**, 8K × 24-bit words seen as 32-bit pairs: even word = bits 31-16 (the top 8 bits unused), odd word = bits 15-0 | `hd68k_adsp_program_r/w` |
| 808000-80BFFF | R/W | **ADSP data RAM**, 8K × 16-bit; a write to word 0x1FFF is the sync trigger (raises the ADSP's IRQ) | `hd68k_adsp_data_w` |
| 810000-813FFF | R/W | **ADSP output buffer** (SOM), one of two 8K-word banks | `hd68k_adsp_buffer_r/w`, bank from control bit 3 |
| 818000-81801F | W | **ADSP control**: bits 0-2 select, bit 3 value. 0, 1 LEDs; 3 output-buffer bank; 5 /BR; 6 /HALT; 7 reset | `hd68k_adsp_control_w` |
| 818060-81807F | W | clear the ADSP interrupt (level 2) | `hd68k_adsp_irq_clear_w` |
| 838000-83FFFF | R | ADSP status: bit 0 low = ADSP interrupt pending, bit 1 low = XFLAG set, other bits 1 | `hd68k_adsp_irq_state_r` |

| B80000-BFFFFF | R/W | 12-bit ADC read / ADC channel select and start | `hd68k_adc12_r`, `hd68k_adc_control_w` |

| C04000-C07FFF | R/W | MSP host interface, reads 0xFFFF (no MSP) | `hd68k_msp_io_r/w` |
| FF0000-FF001F | R/W, high byte | MC68681 DUART (RS-232, the link port) | |
| FF4000-FF4FFF | R/W | **ZRAM**: 2 KB × 16, high byte = M48T02 at 200E, low byte = 2816 EEPROM at 210E, write-protected by ZP1/ZP2 | `hd68k_zram_r/w` |
| FF8000-FFFFFF | R/W | 32 KB work RAM | |

Interrupts (`update_interrupts`, `harddriv_m.cpp`): level 1 MSP (never here), **2 ADSP** (/GINT from the ADSP's special write 6), **3 GSP** (TMS34010 output interrupt), **4 sound** (JSA II, "/LINKIRQ on STUN Runner" in the source comment), **5 timer** (`hd68k_irq_gen`, a periodic interrupt at 32 MHz / 16⁴ / 2 ≈ 244 Hz, line 1465, cleared by the 60C000 write; the vblank itself sets `m_video_int_state`, which `update_interrupts` never reads, so the 68010 sees vertical sync only as /VSYNC in port 0 bit 2), 6 DUART. The 68010 vector table at 0x000000 in `200r/210r` is therefore the first thing to label.

## 4. The TMS34010 GSP

`multisync_gsp_map` (line 619). The GSP addresses bits: a byte is 8 address units, a 16-bit word 16.

| Bit address | What | MAME |
|---|---|---|
| 00000000-0000200F | nothing (hit by the self-test) | |
| 02000000-020FFFFF | **2 bpp pixel expander** write window: a 16-bit write expands 8 two-bit pixels through the mask table, painting `gsp_control_lo[0]` where a mask bit is set; reads return 0 | `hdgsp_vram_2bpp_w`, `init_video` |
| F4000000-F40000FF | control lo: word 0 is the expander colour | `hdgsp_control_lo_w` |
| F4800000-F48000FF | control hi, bit-3-value scheme: 0 shift-register enable, 1 fine scroll (0-7 on multisync), 2-4 palette bank bits 0-2, 7 LED | `hdgsp_control_hi_w` |
| F5000000-F5000FFF | palette lo: red in the high byte, green in the low byte; only 256 entries visible, the bank selects which 256 of 1024 | `hdgsp_paletteram_lo_w` |
| F5800000-F5800FFF | palette hi: blue in the low byte | `hdgsp_paletteram_hi_w` |
| FF800000-FFBFFFFF | **512 KB VRAM**, mirrored at FFC00000-FFFFFFFF | `.ram().share("gsp_vram")`, `.mirror(0x0400000)` |

The GSP has **no ROM**. It is held in reset at power-up (`set_halt_on_reset(true)`), the 68010 writes its program into VRAM through the host interface at C00000 and releases /GSPRES through the NWR latch. The GSP code therefore lives somewhere in the 68k ROMs as a block of 16-bit words, and a copy loop in the 68k code will reveal where; the speedup addresses (idle PC 0xFFF41070, counters at 0xFFF9FC00 and 0xFFFCFC00) say the program runs in the upper mirror of VRAM. Display: 8 bits per pixel, `scanline_multisync` reads a row of 2048 bytes (`rowaddr << 10` words), 512 × 228 visible at 60.2 Hz in the driver's initial parameters (`set_raw(5000000*2, 317*2, 0, 256*2, 262, 0, 228)`, pixel clock 5 MHz with 2 pixels per clock); once the game has programmed the TMS34010's timing registers the screen is 512 × 240, GSP rows 28h-117h (MAME snapshots, docs/08 section 4.1). The VRAM shift-register transfers (`hdgsp_write_to_shiftreg` / `hdgsp_read_from_shiftreg`) implement the TMS34010's bulk row copy. The GSP raises 68010 level 3 (`hdgsp_irq_gen`).

What this means for assets: fonts, the HUD and any bitmap art are either drawn by GSP code from data in the 68k ROMs, or copied through the host port from the 68k ROMs. There is no fixed tile format to decode; the formats are whatever the GSP routines read. Finding them is a milestone (docs/03).

## 5. The ADSP-2100

`adsp_program_map` and `adsp_data_map` (lines 680-699), `hdadsp_special_r/w` (`harddriv_m.cpp` lines 776-838).

- **Program memory** 0x0000-0x1FFF: 8K × 24-bit RAM, written by the 68010 (section 3). 0x2000-0x3FFF reads as nothing ("ROM?"). The ADSP has no boot ROM in this driver: like the GSP, its code is a block inside the 68k ROMs.
- **Data memory** 0x0000-0x1FFF: 8K × 16-bit RAM, shared with the 68010 at 808000. Word 0x1FFF is the command/sync word: the 68010's write triggers the ADSP's interrupt, and the ADSP's idle read of it is the speedup hook.
- **Data memory 0x2000-0x2FFF, the special I/O** (offset & 7): read 0 **/SIMBUF** returns the next 16-bit word of the object ROM stream at `eprom_base + sim_address` and increments; write 1 **/SIMCLK** sets `sim_address`; write 7 **/MP** sets `eprom_base = 0x10000 × data` (three 64K-word pages cover the 384 KB region); write 2 **SOMLATCH** stores a word into the *other* output-buffer bank at `som_address++`; write 3 **/SOMCLK** sets `som_address`; write 5 **/XOUT** a flag bit; write 6 **/GINT** interrupts the 68010 (level 2).
- Control from the 68010: reset, /HALT, /BR and the output-bank flip (section 3).

So the pipeline is: the 68010 fills ADSP data RAM with the frame's scene (and writes 0x1FFF), the ADSP streams object geometry from the serial ROMs, transforms it and writes a display list into the SOM buffer, and signals /GINT; the 68010 then flips the output bank (ADSP control line 3, 0x02C3FA/0x02C408) and copies the list into the GSP's command buffer (docs/08 sections 0 and 2). MAME's `deferred_adsp_bank_switch` (`harddriv_m.cpp` line 634) logs the SOM buffer under `LOG_COMMANDS`: a word count, `(cmd, a, b, c)` records, slope pairs with a count, and an index table. It reads every command as a polygon, so image commands come out wrong; docs/08 section 1.6 checks it field by field.

## 6. The JSA II sound board

`atarijsa.cpp` header (the "Atari Audio Board II" 6502 memory map) and `atarijsa2_map` (line 116):

| 6502 address | What |
|---|---|
| 0000-1FFF | RAM |
| 2000-2001 | YM2151 |
| 2800 (mirror 01F9) | OKI M6295 read (/RDV) |
| 2802 | command byte from the 68010 (/RDP) |
| 2804 | **/RDIO**: bit 7 self-test, 6 NMI state, 5 output buffer full, 4-2 +5V, 1 coin 2, 0 coin 1 |
| 2806 | IRQ acknowledge (read or write) |
| 2A00 | OKI write (/WRV) |
| 2A02 | response byte to the 68010 (/WRP) |
| 2A04 | **/WRIO**: bits 7-6 ROM bank for 3000-3FFF, 5-4 coin counters 2 and 1, 3 OKI pin 7 ("voice frequency", `set_pin7`), 2 OKI reset (active low), 1 OKI bank bit 0 (JSA III only), 0 YM2151 reset (active low), per `wrio_w` |
| 2A06 | **/MIX**: bits 7-6 right OKI bank (JSA IIIs only), 5 low-pass filter enable (not emulated), 4 OKI bank bit 1 (JSA III only), 3-1 YM2151 volume 0-7, 0 OKI volume (1.0 when set, 0.5 when clear) per `mix_w` |
| 3000-3FFF | banked ROM: 4 pages of 4 KB from the first 16 KB of `136070-2123.10c` (`configure_entries(0, 4, base, 0x1000)`) |
| 4000-FFFF | ROM, file offset 0x4000-0xFFFF |

The 6502 gets a periodic IRQ at 3.579545 MHz / 4 / 16 / 16 / 14 ≈ 249.7 Hz and the YM2151's IRQ. The 256 KB of ADPCM is not banked on JSA II (`atari_jsa_ii_device` has no OKI bank; the 6295 sees 256 KB directly). Ports: `jsa:JSAII` has the coin inputs; stunrun routes coins through the main board instead ("stunrun has its own coins").

## 7. Inputs and outputs the code will reference

From `INPUT_PORTS_START(stunrun)` (line 1084): port 0 as in section 3 with SW1's eight switches unlabelled by MAME; `a80000` button 1, button 2 and start; ADC channel 0 = stick X, channel 2 = stick Y (sensitivity 25, centred 0x80); channels 1 and 3-7 and all 12-bit channels unused. Outputs through WR0/WR1: lamps and coin counters.

## 8. Questions this map leaves open for the plan

1. Where in the 768 KB are the GSP program, the ADSP program and the data each one needs? The 68k copy loops will tell; until then the whole image is "68k data".
2. What is the object ROM format (the records the ADSP streams through /SIMBUF)? That decides what "assets as meshes" means. The ADSP code's /SIMCLK / /SIMBUF reads are the entry point.
3. What does the GSP draw from (SOM display list from the ADSP, plus text and HUD from the 68k)? The GSP code is the only reader of VRAM, so its routines define every picture format.
4. Does any 68k code run from RAM (FF8000)? Hard Drivin' games copy little; check before assuming all 68k code is in ROM.
5. The DUART: a link port for a two-player cabinet pair? Which code paths use it decides whether link code is dead in a single cabinet.
