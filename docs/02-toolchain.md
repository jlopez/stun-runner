# Toolchain

**Date**: 2026-11-04. The precedent is the Spindizzy assembler-source programme (`~/git-repos/personal/spindizzy`, `docs/26-assembler-source.md`, `CLAUDE.md` section 12): one assembler per CPU chosen for exact byte control, bytes always from the ROM files and never from a database, IDA as the annotation database with names synced from the source, an emulator as the oracle, and `make check` as the definition of done. What is new here is that four instruction sets share one ROM image (docs/01), two of which have no off-the-shelf assembler.

## 2. Assemblers

### 68010: vasm, Motorola syntax (recommended)

`vasmm68k_mot` from <http://sun.hasenbraten.de/vasm/> (`make CPU=m68k SYNTAX=mot`). Reasons, in order:

- **Byte control.** `-no-opt` disables every instruction optimisation, so `move.l #0,d0` stays a 6-byte `move`, a `bra` stays the width written, and absolute addressing stays `.l` or `.w` as written. The source states the encoding; the assembler does not choose it. asm68k-compatible assemblers and GNU `as` both optimise or relax by default, and `as` additionally needs a linker script to produce a flat binary.
- **Flat output.** `-Fbin` writes the image directly; no linker, no object format. The byte-split into `200x`/`210x` files is a tool step (`tools/split-roms`), not an assembler feature.
- **Syntax.** Motorola syntax with `dc.b/dc.w/dc.l`, `ds`, `even`, `incbin`, local labels (`.label` and `1$`), `rs` structures, macros and conditional assembly, which is the family Atari's own 1980s 68k sources used (verify against any surviving Atari listing before claiming more than "same family").
- **Listing and symbols.** `-L` listing for the coverage check, `-Fvobj`/symbol dumps for the label check, like Spindizzy's `make coverage` and `make labels`.
- **CI.** Not packaged by apt or brew; CI builds it from the pinned release tarball, verifies its sha256 and caches the binary (docs/04 section 6). Guards: vasm's Motorola syntax rejects `<>` in `if` (use `!=` or `assert *=$addr,"msg"`); `incbin "file",offset,length` resolves the path from the source file's directory (docs/04 section 3).

Alternatives considered: asm68k (Sega-era, Windows binary, Wine; no), GNU as + ld (relaxation and a linker script for no gain), ASL/Macroassembler AS (capable, but its Motorola mode also optimises unless told per instruction).

### 6502 (JSA II): 64tass

As in Spindizzy: `64tass -q -C -b` for a flat binary, `-L` listing, case-sensitive labels like IDA's, `.logical`/`.here` for the four banked 4 KB pages that all assemble for 3000-3FFF but sit at file offsets 0x0000-0x3FFF, `.cerror` guards per region, `.binary` for sample tables. The Spindizzy tools (`bytecheck.py`, `coverage.py`, `labelcheck.py`, `scaffold.py`, `ida_sync.py`) are the models to port.

### TMS34010 (GSP) and ADSP-2100: in-repo assemblers, after the code is understood

No maintained assembler exists for either (TI's `gspa` and Analog Devices' `asm21` are DOS-era and not redistributable). Decision proposed: **three tiers of source**.

1. 68k and 6502: readable assembler from the first milestone.
2. GSP and ADSP programs: start as **extracted binary blobs** inside the 68k tree (`incbin` of `build/gsp/program.bin` and `build/adsp/program.bin`, both produced from the ROM by a tool with a `.cerror`-style check on their position and size), each with an **annotated listing** generated by `unidasm` and hand-commented in a sidecar file.
3. Once each program is understood, a **Python assembler** per ISA in `tools/asm34010/` and `tools/asm2100/`, proven by round-tripping every instruction form the program uses against `unidasm` (assemble → disassemble → same text; disassemble → assemble → same bytes), and the blob is replaced by source. The TMS34010 instruction set is about 130 forms with a regular 16-bit encoding; the ADSP-2100 has 24-bit instructions in about 30 formats. Both are bounded jobs, and the test oracle (unidasm) exists.

This keeps `make check` green at every step: the image is byte-identical whether a block is source or blob.

## 3. Disassembly and annotation

- **68010**: IDA `mc68k`, loaded as a flat binary at 0x000000 with the twelve files interleaved by `tools/merge-roms` (bytes come from the files; the merged image is a build artefact, never committed). Headless access through idalib exactly as Spindizzy's `ida/headless/__init__.py` (copy the database to a temp dir, `run_auto_analysis=False`, never save unless `write=True`). The `.i64` is committed through Git LFS, packed, with the exports (`functions.jsonl`, `.asm` listing) regenerated by `ida.headless.export`.
- **6502**: IDA `m65` on the 64 KB file with the 4000-FFFF window at its address and the four bank pages as separate segments. Or 64tass-first with a sidecar listing, if the sound program turns out small: decide at the first sound milestone.
- **ADSP-2100**: try IDA's `ad218x` (ADSP-218x is a superset of the 2100 instruction set; the 2100 lacks the 218x's extra modes, so a 2100 program should decode cleanly). If it does not, `unidasm -arch adsp2100` and a sidecar.
- **TMS34010**: `unidasm -arch tms34010` on the extracted program, at its VRAM bit address. Annotation lives in a sidecar file the listing tool merges (names, comments per address), which is also what the later assembler consumes. Writing an IDA processor module in Python is possible but is a project of its own; not planned until the GSP code demands cross-references at scale.
- **Names flow one way once source exists**: source → IDA (`make ida-sync`, as Spindizzy's `tools/asm/ida_sync.py`). Before source exists for a region, IDA is the truth for that region and the scaffold drafts from it.

## 4. MAME as the oracle

- **Set location**: `~/archive/261104-stun-runner/roms/stunrun/` (the 25 loose files) or `~/archive/261104-stun-runner/roms/stunrun.zip`; `~/.mame/mame.ini` already names that `rompath`. `mame -verifyroms stunrun` and `tools/check-roms` must both pass before any work starts.
- **Run**: `mame stunrun`; `-debug` opens the debugger with all four CPUs (`focus`, `dasm`, `save`, `dump`, `wp` on the host-interface and ADSP windows). `-window -nothrottle` for fast runs; `-str N` for timed runs; `-snapshot` for pictures.
- **Dumps**: the debugger's `save <file>,<start>,<len>,<cpu>` dumps VRAM, ADSP program and data RAM and the SOM buffers; a Lua script (`-autoboot_script`) can dump at a breakpoint without the GUI. These dumps are the evidence that a copy loop in the 68k code put the GSP program at a given address, that an extracted blob equals what runs, and later that a rebuilt ROM behaves identically (same VRAM after N frames with the same input script, `-playback`).
- **unidasm**: build from the MAME source tree matching 0.289 (`make TOOLS=1 unidasm`, or the full `make TOOLS=1`); it is the disassembler for all four ISAs (`-arch m68000`, `m6502`, `tms34010`, `adsp2100`) and the round-trip oracle of section 2. Install it to `~/.local/bin` or next to brew's `mame`; record the commit here.
- **Logging**: `-log` with MAME's `logerror` output names every ADSP sync, bank flip, /GINT and GSP control write (the driver is chatty), which is a timeline of the frame pipeline for free.

## 5. The byte-identical build check

`make` assembles the four programs and splits the result into the 25 files of the set under `build/roms/stunrun/`; `make check` compares each with the reference by SHA-1 and CRC-32 against `tools/romsets/stunrun.json` (the same hashes MAME lists), and on a mismatch reports per file the first differing offset and the count, with the address in the CPU's own space (68k byte address for `200x/210x` pairs, 6502 address for `10c`, ADSP word index for the object ROMs). Zero differences over all 25 files, or it is not done. `make coverage` reports per region file how many bytes come from instructions, from data statements, from `incbin` blobs and from fills, so the "blob" share is a number that must only go down. `make labels` checks that every IDA name is a label at its address. `make test` runs the converters' round trips (assets → bytes → assets, assemblers → unidasm → assemblers). The Makefile, the five images, the trees and the checks as built in milestone 1 are in docs/04-build.md.

## 6. Repository conventions carried over

uv-managed Python 3.11+, ruff and mypy; `build/` ignored; the IDA database and any dump over a few hundred KB through Git LFS; branch per leg, PR, squash with a holistic message; `docs/NN-*.md` per leg, decisions in `CLAUDE.md`. ROM content never enters the repository, not as files, not as hex in a document, not as an `incbin` of the archive path: the build reads the reference set only to compare.
